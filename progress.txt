## Codebase Patterns

- Preserve canonical inventory field semantics across all tenants: Item, Placa Anterior, Descrição, Marca, Modelo, NS, Local, CC, Complemento, Observação.
- Treat tenant-specific behavior as configuration first, not as branching logic in the validation core.
- Keep one generic validation engine for all tenants.
- Normalize source input into canonical field names before running validation rules.
- Derive `flag_item_coletado` and `flag_item_cadastrado_do_zero` before executing row-level validation.
- Prefer rule-based validation with reusable abstractions over hardcoded validation chains.
- Keep API handlers thin and delegate orchestration to services.
- Keep validation logic, job orchestration, and report rendering in separate modules.
- Preserve the distinction between collected items and zero-created items as a core domain concept.
- Use `progress.txt` to record assumptions, gotchas, and reusable learnings for future iterations.
- Only mark a story as passed when implementation is complete and quality checks pass.
- Quality gates are: `ruff check app/` (lint) and `pytest app/tests/` (tests). No mypy/pyright installed.
- Run `ruff check --fix app/` to auto-fix import sorting issues before committing.
- Use `Path(__file__).resolve().parent` for module-relative paths instead of hardcoded relative paths.
- Tenant configs use typed Pydantic sub-models (`CategoryConfig`, `LLMConfig`) — keep them in `app/core/tenant_config.py`.
- Clear `RULE_REGISTRY` in test setup/teardown to avoid cross-test contamination.
- Use `register_rule()` from `app.core.registry` to add rules; the engine resolves them by name from `TenantConfig.enabled_rules`.
- Pydantic v2 copies dict values on model construction — pass shared_context between ValidationContext instances explicitly for cross-row caching.
- Cross-row rules (e.g., duplicate detection) should cache computed data in `shared_context` to avoid re-computing per row.
- Use Protocol-based abstractions for external service clients (e.g., LLM) to enable testability without mocking internals.
- Tenant-specific prompt files live under `app/tenants/{tenant_id}/prompts/`; reference via `prompt_file` in tenant YAML.

## Project Context

This project is a multi-tenant inventory validator.

Primary goals:
- support tenant-specific validation without duplicating the core engine
- preserve canonical inventory domain semantics
- support deterministic validation and optional LLM audit
- support asynchronous validation jobs
- generate operationally useful outputs for correction workflows

Canonical fields:
- Item
- Placa Anterior
- Descrição
- Marca
- Modelo
- NS
- Local
- CC
- Complemento
- Observação

Derived concepts:
- flag_item_coletado
- flag_item_cadastrado_do_zero

Expected architectural direction:
- app/core/
- app/rules/
- app/services/
- app/api/
- app/workers/
- app/tenants/
- tests/

## Initial Notes

- This repository is intended to be developed iteratively through Ralph loop style execution.
- The PRD in `prd.json` is the source of truth for story order and acceptance criteria.
- The default tenant must remain a working baseline for future tenant-specific extensions.
- Tenant variation should prefer config for mappings, thresholds, categories, critical checks, enabled rules, and LLM settings.
- Do not scatter tenant names through the validation core.
- Avoid refactoring unrelated areas during early foundation stories.
