## Codebase Patterns

- Preserve canonical inventory field semantics across all tenants: Item, Placa Anterior, Descrição, Marca, Modelo, NS, Local, CC, Complemento, Observação.
- Treat tenant-specific behavior as configuration first, not as branching logic in the validation core.
- Keep one generic validation engine for all tenants.
- Normalize source input into canonical field names before running validation rules.
- Derive `flag_item_coletado` and `flag_item_cadastrado_do_zero` before executing row-level validation.
- Prefer rule-based validation with reusable abstractions over hardcoded validation chains.
- Keep API handlers thin and delegate orchestration to services.
- Upload preflight should run in `app/services/validation_service.py` before `job_service.create_job(...)`; on failure, return a top-level `preflight` payload with detected/missing columns so the frontend can render inline corrections without creating a doomed job.
- Accept XLSX uploads by converting them to tenant-configured CSV at ingress in `app/services/validation_service.py`; keep downstream job execution, duplicate correction, and report flows on the shared CSV artifact.
- Keep validation logic, job orchestration, and report rendering in separate modules.
- Preserve the distinction between collected items and zero-created items as a core domain concept.
- Use `progress.txt` to record assumptions, gotchas, and reusable learnings for future iterations.
- Only mark a story as passed when implementation is complete and quality checks pass.
- Quality gates are: `ruff check app tests` (lint) and `pytest` (tests). No mypy/pyright installed.
- Keep CI as three explicit jobs: backend (`ruff` + `pytest`), frontend (`npm run typecheck`/`lint`/`test`), and an API-level smoke probe (`pytest tests/test_api.py -k authenticated_smoke_login_upload_and_fetch_result`) so the authenticated main flow is reproducible without separate services.
- Run `ruff check --fix app tests` to auto-fix import sorting issues before committing.
- Use `Path(__file__).resolve().parent` for module-relative paths instead of hardcoded relative paths.
- Tenant configs use typed Pydantic sub-models (`CategoryConfig`, `LLMConfig`) — keep them in `app/core/tenant_config.py`.
- Clear `RULE_REGISTRY` in test setup/teardown to avoid cross-test contamination.
- Use `register_rule()` from `app.core.registry` to add rules; the engine resolves them by name from `TenantConfig.enabled_rules`.
- Pydantic v2 copies dict values on model construction — pass shared_context between ValidationContext instances explicitly for cross-row caching.
- Cross-row rules (e.g., duplicate detection) should cache computed data in `shared_context` to avoid re-computing per row.
- Use Protocol-based abstractions for external service clients (e.g., LLM) to enable testability without mocking internals.
- Tenant-specific prompt files live under `app/tenants/{tenant_id}/prompts/`; reference via `prompt_file` in tenant YAML.
- Parse optional YAML frontmatter for tenant prompt files at load time and default legacy prompts to a stable version token so LLM audit/report metadata stays reproducible without breaking older prompts.
- LLM response caching is tenant-configured with `llm.cache_ttl_seconds`; cache keys and persistence live in `app/core/llm_cache.py`, storage path comes from `VALIDATOR_LLM_CACHE_PATH`, and `force_refresh` job params bypass cache reads while refreshing successful writes.
- LLM fallback model selection is tenant-configured with `llm.fallback_model`; retry only transient failures (timeouts, HTTP 429, HTTP 5xx), and preserve attempted model sequence plus primary/final failure details in warning issue metadata.
- Safe validation parallelism should stay limited to isolated row-level phases (currently `llm_audit`); keep cross-row rules and shared aggregations in the serial pass, then merge only deterministic metadata back into shared context.
- When parallelizing preview-time validation, ensure the batch size is at least the configured worker count; otherwise single-row batches neutralize the intended throughput gain.
- Frontend media parsing should stay frontend-only over raw row payloads: preserve all browser-renderable sources in order (HTTP/HTTPS, `data:image`, raw base64) and ignore local mobile-app paths like `/data/user/...`.
- Duplicate-result severity UI should reuse a shared conflict helper so red cards and duplicate filters stay aligned on the same rule.
- Frontend result filtering/search should stay in shared presentation helpers over the existing result payload, and local filters/search should reset when `currentJobId` changes.
- Frontend category result filters derive available categories from `CATEGORY_*` grouped problem codes unless the backend explicitly adds category metadata to the result payload.
- Mutable review markers for completed results should be stored as tenant-scoped sidecar files under `results/{tenant_id}/{job_id}/review_flags.json` and overlaid into the result payload at read time, leaving generated JSON/PDF artifacts immutable.
- Manual correction history should be persisted as job-scoped audit events with structured diffs and overlaid into `GET /jobs/{job_id}/result`; safe rollback stays LIFO so only the latest eligible correction can be undone before the next reprocess.
- Low-volume operational persistence (jobs, audit events, issued API keys, managed operators) should go through `app/core/operational_sqlite.py` when `VALIDATOR_SQLITE_PATH` is configured; keep the legacy `VALIDATOR_*_STORE_PATH` JSON env vars as migration fallback.
- Keep artifact-local outputs on the filesystem even when operational metadata moves to SQLite: uploaded CSVs, generated result/report files, per-job `review_flags.json`, and the LLM cache remain file-based.
- Operational artifact retention should stay in `app/services/retention_service.py` with env-backed `RetentionPolicy`; use `GET /retention/plan` for dry-run inspection and `POST /retention/cleanup` for execution.
- Retention cleanup must protect queued/running jobs, recently updated artifacts, and jobs with `preserve_artifacts=true` before deleting uploads/results/reports/review_flags or pruning LLM cache entries.
- Frontend review-marker filtering should stay in `frontend/src/lib/presentation.ts` over `review_flags`, and local review filters should reset together with search/result filters when `currentJobId` changes.
- For `Nomes iguais`, duplicate resolution should be framed as consolidation: keep one physical CSV row only as an implementation detail, ignore photo/media and date/time enrichment, and preserve the survivor's non-empty allowed value on conflicts.
- Bulk consolidation over duplicate groups should stay conservative for now: only process `Nomes iguais` groups with exactly 2 occurrences, and execute them from the highest row indices downward so CSV reindexing does not invalidate the remaining groups.
- Structured logging flows through `app/core/logging.py`: use `get_logger("layer_name")` + `log_event(logger, "<layer>.<event>", tenant_id=..., job_id=..., duration_ms=..., error=...)` so every emission shares the canonical fields and optionally picks up the current request_id from the contextvar.
- Cross-request correlation comes from `app/api/middleware.py` (request_id contextvar + `X-Request-ID` header echoed back on responses); do not introduce a parallel request-id mechanism.
- Prometheus instrumentation should stay centralized in `app/core/metrics.py`, remain gated by `VALIDATOR_METRICS_ENABLED`, and never use `job_id`/`request_id` as metric labels.
- Keep `/health` thin by delegating probes to `app/core/health.py`; uploads/results/job_store are critical checks, while LLM reachability is an optional degradation path that is opt-in per tenant via `llm.healthcheck_enabled`.
- LLM health probes should stay conservative: use low-cost provider reachability checks with aggressive timeout defaults instead of triggering a full audit completion.
- Tenant-scoped API auth should derive tenant context from `X-API-Key`; any `tenant_id` request parameter is only a hint and must be rejected on mismatch.
- Persist auth-related operational metadata with the configured `api_key_id`, never the raw API key secret.
- Middleware that enforces custom auth headers must allow unauthenticated `OPTIONS` preflight requests and keep `/health` and `/metrics` public.
- Login-issued API keys flow through `app/services/auth_service.py`: tenant operators live in `TenantConfig.operators` with PBKDF2 password hashes, `/login` is public, issued keys are stored by hash only via the shared SQLite store or the legacy `VALIDATOR_API_KEY_STORE_PATH` fallback, and middleware resolves issued keys before legacy tenant `api_keys`.
- Production auth hardening lives in `app/core/auth_policy.py`: `VALIDATOR_ENV=production` disables legacy YAML `api_keys` and seed YAML operators by default; break-glass exceptions are `VALIDATOR_ALLOW_LEGACY_API_KEYS_IN_PRODUCTION` and `VALIDATOR_ALLOW_SEED_OPERATORS_IN_PRODUCTION`.
- Frontend issued `X-API-Key` secrets should remain memory-only by default in `frontend/src/lib/api.ts`; persist the raw secret only when `NEXT_PUBLIC_PERSIST_RAW_API_SESSION=true` is explicitly configured for a controlled environment.
- Issued key lifecycle policy belongs in `tenant.auth.issued_api_key_ttl_seconds`; `AuthService` owns issue/expire/revoke transitions plus audit emission, and middleware should reject expired or revoked issued keys before falling back to legacy tenant `api_keys`.
- When issued API keys are persisted in shared storage, `AuthService.inspect_issued_api_key()` must reload records on cache miss before returning `MISSING`; otherwise a fresh login issued by another process/pod can be rejected immediately as `Invalid API key`.
- Derive upload/result/report artifact paths through shared tenant-scoped helpers (`uploads/{tenant_id}/...`, `results/{tenant_id}/...`) and keep a legacy root-path fallback during storage-layout migrations.
- Tenant text alias dictionaries belong in `tenant.normalization`; normalize `Marca`/`Modelo` in the core pipeline before rules and preserve the original source values in `ValidationContext.raw_row`.
- When a rule needs to infer the expected `Marca` from `Modelo`, keep the tenant-owned dictionary in `tenant.normalization.model_brands` keyed by canonical model names and compare against the already-normalized canonical row value.
- New tenant-owned rule config should use typed Pydantic sub-models in `app/core/tenant_config.py`; validate regex-like entries during tenant load so jobs do not fail mid-validation.
- Frontend auth should stay centralized in `frontend/src/lib/api.ts`: treat `/login` as the only public call, inject the issued `X-API-Key` for the workspace from shared helpers, and cover UI auth states with Vitest `jsdom` component tests plus `frontend/src/test/setup.ts`.
- Protected frontend downloads must use authenticated helpers in `frontend/src/lib/api.ts`; raw `<a href>` links do not send the issued `X-API-Key` header.
- Client-generated operational CSV exports should be built from the same `frontend/src/lib/presentation.ts` helpers that power the on-screen filters, then downloaded through a shared browser helper in `frontend/src/lib/api.ts`.
- Tenant-scoped operational panels in the frontend should fetch through authenticated helpers in `frontend/src/lib/api.ts` and keep local filter/reset behavior in `frontend/src/lib/presentation.ts`, resetting context-sensitive filters when the tenant or `currentJobId` changes.
- For operator-facing frontend flows, keep the main path step-based (`Enviar planilha` -> `Acompanhar lote` -> `Revisar resultado`) and push secondary panels like audit behind an explicit disclosure to reduce visual noise.
- Prefer operator-facing labels like `empresa` and `lote` in the primary UI copy; reserve backend terms like `tenant` and `job` for technical or support contexts only.
- Frontend tenant-scoped workspaces must initialize their active tenant from the authenticated session, not from a hardcoded `default` fallback; otherwise optional panels can fire a mismatched tenant request before `/tenants` finishes loading and trigger false auth failures for non-default operators.
- Session renewal routes through `AuthService.renew_api_key` + `POST /api-keys/renew`; emit `api_key_renewed` linking predecessor to successor, propagate `expires_at` into the frontend `LoginResponse`, and warn the operator before expiration without forcing a logout.
- Frontend session invalidation should react to true credential failures (`Invalid/Expired/Revoked API key`), not to generic `403` authorization mismatches like `API key does not grant access to tenant ...`; those should surface as local errors without logging the operator out.
- Frontend admin panels should stay opt-in over the operational workspace, gate platform-only controls from `session.role`, and keep ordinary `403` permission failures as inline feedback instead of forcing logout.
- Job reprocess lineage belongs on `JobRecord.parent_job_id` + `latest_retry_job_id`; `JobService.register_reprocess_link` owns both the link mutation and the `job_reprocessed` audit event, so new reprocess orchestrations stay tenant-agnostic and route through the shared helper instead of duplicating lineage bookkeeping.
- Validation job cancellation should use cooperative checkpoints through long service/engine loops; do not rely only on batch-end polling for large CSV reads, global indexing, row validation, or artifact preparation.
- Persisted jobs loaded as `running` with `cancel_requested=true` should be finalized as `canceled` by `JobService` so restarts do not leave inactive work stuck as "Cancelando".
- Frontend job progress/ETA copy should stay in `frontend/src/lib/presentation.ts`, and the actively opened lot should keep a slower hidden-tab polling cadence so terminal notifications still work after tab switches.
- Frontend Vitest runs vanilla `tsc --noEmit` with `jsx: preserve`, so any component rendered by `@testing-library/react` must `import React from "react"` explicitly — otherwise the compiled output still references a missing `React` identifier at runtime.
- Tenant-scoped operator management should keep seed operators in tenant config as bootstrap data and overlay runtime create/disable/password changes through `AuthService` storage instead of mutating tenant YAML from the API.
- RBAC/permission decisions should stay in `AuthService`; FastAPI routes pass authenticated actor context plus target tenant/action and then use the canonical tenant returned by the service.
- Environment-driven first-admin bootstrap should run through `AuthService` over persisted operator storage (`VALIDATOR_SQLITE_PATH` or `VALIDATOR_OPERATOR_STORE_PATH`), use `VALIDATOR_OFFICIAL_TENANT_ID` as the canonical tenant target, and stay idempotent unless `VALIDATOR_BOOTSTRAP_ADMIN_FORCE_RESET=true` is set explicitly.
- Public first-run setup routes are `GET /setup` and `POST /setup`; keep them unauthenticated in `app/api/auth.py`, backed by `AuthService`, and closed whenever any persisted operator record already exists.
- First-run administrator setup must require persistent operator storage, store only password hashes and minimal operator metadata, use `VALIDATOR_SETUP_TOKEN` for optional published-environment protection, and use SQLite atomic insertion for cross-process single-use protection.
- Disabling an operator should revoke that operator's active issued API keys inside the same auth-service flow so middleware and audit behavior stay consistent immediately.
- First-login password-setup enforcement should stay centralized in `app/api/auth.py`; allowlist only the public invite/setup routes and the password-setup completion route instead of sprinkling auth exceptions across handlers.
- Persist managed-user auth state on operator records (`must_change_password`) and store invitation tokens hashed-only in the operational store/SQLite; never persist raw invite tokens or mix invite payloads into the operator JSON schema.
- Public auth hardening should stay in `AuthService`: routes pass request origin, `/login` remains generic for enumeration resistance, and lockout logic should not be reimplemented in FastAPI handlers.
- Password recovery tokens should follow the same hash-only persistence pattern as invitations, with short TTLs and single-use semantics enforced in shared operational storage.
- Tenant renames should be handled with declarative aliases in `TenantConfig` plus shared canonicalization in `app/core/tenant_loader.py`; service-layer storage should migrate persisted tenant_ids to the canonical value on load instead of introducing tenant-specific branches.
- Tenant administration metadata should be a runtime overlay (`tenant_id`, `display_name`, `aliases`, `disabled`) in operational storage; YAML/file-based tenant configs remain the source for validation rules, and runtime-created tenants inherit the default validation profile without seed API keys/operators.
- Managed validation profiles now persist as tenant-scoped drafts and immutable published versions in `app/core/tenant_profile.py`; `load_tenant_config()` overlays only the latest published profile, never drafts.
- Profile admin services should load the tenant base with `include_profile=False` before validating draft publication or rollback, so existing published overlays do not mask invalid profile changes.
- Use `load_tenant_config(..., include_disabled=True)` only for admin/history paths that must see disabled tenants; normal tenant loading should reject disabled tenants so login, legacy API keys, and issued sessions stop working immediately.
- Administrative audit should stay in the shared `AuditService`: classify admin-sensitive events in `app/core/audit.py`, store structured `details` like `actor_operator_id`, `target_operator_id`, and `result` for filters, and enforce global-vs-tenant audit visibility through `AuthService` instead of creating a second audit store.
- Dedicated worker mode should claim jobs through the shared SQLite-backed `JobService` lease path; keep API routes enqueue-only in that mode and use inline/background execution only as the local/test fallback.

## Project Context

This project is a multi-tenant inventory validator.

Primary goals:
- support tenant-specific validation without duplicating the core engine
- preserve canonical inventory domain semantics
- support deterministic validation and optional LLM audit
- support asynchronous validation jobs
- generate operationally useful outputs for correction workflows

Canonical fields:
- Item
- Placa Anterior
- Descrição
- Marca
- Modelo
- NS
- Local
- CC
- Complemento
- Observação

Derived concepts:
- flag_item_coletado
- flag_item_cadastrado_do_zero

Expected architectural direction:
- app/core/
- app/rules/
- app/services/
- app/api/
- app/workers/
- app/tenants/
- tests/

- This repository is intended to be developed iteratively through Ralph loop style execution.

- Do not scatter tenant names through the validation core.
- Avoid refactoring unrelated areas during early foundation stories.
